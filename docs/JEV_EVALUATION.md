# Jev 的 XYZ 控制：分层后能搬运，但放置还需改进

`jev-1.13.0` 在新的**分层 XYZ**试跑中完成了仿真任务：先选当前子目标，再同时选择 X、Y、Z 和夹爪通道。此前平铺 21 个动作的试跑没有抓起方块。两次试跑说明控制接口和任务分解值得改进，不能据此推算通用成功率。

## 分层 XYZ 实际做了什么

2026-09-20，`transfer`、seed 7，输入为仿真坐标和接触状态，无相机，安全预演开启，概率门槛 0，预算 160 步。

| 模型 / 控制版本 | `jev-1.13.0` / `hierarchical-xyz-v1` |
| 动作 / API 请求 | 89 / 178；每步一次子目标、一次四通道请求 |
| 请求中位延迟 / 整局实际用时 | 361 ms / 72.43 秒，headless `speed=0` |

| 拦截动作 / 规则代选 | 0 / 0 |

**这局不是一次干净的精确放置。** 第 81 步下放时失去双侧接触，方块落到托盘上；第 82 步模型选择接近并张爪，第 83–89 步选择撤离。它没有选择 `release` 子目标。现有物理成功条件确实满足，但仍需改善抓持与下放稳定性。

## 哪部分由模型决定？

- **模型每步选子目标。** 接近、抓取、抬升、搬运、下降、松爪、撤离、完成，八个选项始终可选，没有程序阶段计数器替它选。
- **模型再选四个通道。** 每个方向选负向、保持或正向；夹爪选张开、保持或闭合。程序保留错误方向，不偷偷纠正。
- **程序提供任务知识和执行约束。** 提示词解释抓取前先对齐、抓稳后再搬运；代码计算测量误差与参考点，每轴步长限制为 2–12 mm，并处理 IK 和安全检查。

这是有任务知识指导的模型决策，不是模型从零学会机器人控制。子目标与动作通道的概率分别展示，不相乘成“整步成功率”。停止、低概率暂停或无效响应时，不切换到规则策略。

2026-09-20，`transfer` 任务、seed 7，使用仿真坐标和接触反馈，无相机；模型每步从固定的 21 个位移、夹爪候选中选择。安全预演开启，概率门槛为 0，最多执行 40 步，没有规则策略代选动作。

## 排查发现了两类问题

**动作选择本身有误。** 初始夹爪比方块高约 20 cm，原始输入的独立探测却把“闭合夹爪”选为 66%。改写为英文目标、自然语言动作描述、补充位移数字，都没有纠正第一步。把空间关系直接说清楚后，三个探测都改选了下降；但完整的试验仍在未抓住方块时转向托盘。这个提示原型没有作为“已修好规划”合入主流程。

官方也说明 [Jev 1.13 不擅长精确数字计算和多层间接推理](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。这里需要继续验证更合适的状态表达和任务分解，不能靠改一个成功标记或加入规则代选来展示模型能力。

**API 选择与公布概率偶尔不一致。** 另一轮诊断收到的 `choice` 是 `y_neg_40`，其概率为 18%，而 `z_neg_40` 为 19%。原适配器要求选择必须是最高概率，因此中止。

现在对 Jev 保留 API 的原始选择和概率，并在界面、导出记录中标出不一致；不会替模型改选最高项。未知动作、缺失候选、负值、非有限数值或明显不归一的概率仍会拒绝。回归测试使用实际捕获的响应，检查执行的是 API 返回的动作。修复接入问题不会自动提高规划质量。

## XYZ 与视觉是两件事

XYZ 表示模型怎样控制机械臂；视觉表示模型从哪里取得信息。读取坐标也能选择 XYZ。当前 [Jev 官方接口只接收文本，不支持图像](https://docs.typesafe.ai/concepts/state)，可使用仿真坐标或本地 RGB-D 检测器估计的坐标；直接看图的路径仍由支持图像的 Chat / Claude 接口承担。

## 复现

先在工作台保存 TypeSafe Jev 连接，再运行以下命令。它会产生真实模型调用，并保存成功或失败的完整记录。

```bash
python scripts/planning_trial.py --provider jev --saved-connection \
  --control-mode hierarchical --observation privileged --cameras none \
  --seed 7 --max-cycles 160 --timeout 360 --output runs/jev-hierarchical
```

旧控制方式仍保留：将 `--control-mode` 改为 `incremental`，旧试跑的预算为 40 步。模式、预算和输入均写入实验记录。
